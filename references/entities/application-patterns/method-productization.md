# Method productization / software-in-service

Method productization packages expert judgment so it can be configured,
applied, reviewed, and taught repeatedly. The repeating unit is one application
of the method for a buyer or operating instance.

## Use it when

Use it after the method has worked in real delivery and its decisions can be
made explicit without pretending that software rails are the expertise. A
[Knowledge Bundle](https://github.com/RinDig/icm-architect/blob/e5313c308522ff9c4646a17b06fb1ddb0d844917/references/forms.md#4-knowledge-bundle--the-product-is-the-knowledge)
holds the method; a
[Pipeline](https://github.com/RinDig/icm-architect/blob/e5313c308522ff9c4646a17b06fb1ddb0d844917/references/forms.md#1-pipeline--the-production-line)
applies it. Several products or buyer types may sit beneath an
[Umbrella](https://github.com/RinDig/icm-architect/blob/e5313c308522ff9c4646a17b06fb1ddb0d844917/references/forms.md#2-umbrella--a-portfolio-of-pipelines).

## What it contains

- the method, decision rules, quality bar, and supporting examples;
- configuration inputs for one buyer or instance;
- execution stages that make judgment visible;
- reviewed delivery artifacts;
- a controlled proposal path for sanitized learning.

The flow is: configure → apply method → review → deliver → capture candidate
learning → separately improve the factory. See
[Method factory and instances](../compositions/method-factory-instances.md).

## Human and product boundary

A person approves delivery and any promotion into the shared method. Keep
client facts inside their instance. Permissions, metering, isolation,
observability, and upgrades belong to deployable software, not Markdown.
